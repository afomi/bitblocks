Recount an election yourself

You can check a Bitblocks election on your own computer, from its archive alone. You don't have to trust Bitblocks, or whoever ran the election. The recount makes no network calls, so it works offline and after our servers are gone.

What you need

  • A computer with Python 3.8 or later. A Mac or Linux machine already has it: open Terminal and type python3 --version. On Windows, install it free from python.org, then use py where this page says python3.
  • The election's archive: a folder of files, linked from the election's page.
  • The election's archive_sha256: a 64-character code in the result record, shown on the election's page.
  • The recount tool, one file: recount.py. Save it next to the archive folder. If the archive came as a zip, a copy is already inside it, beside this guide.

Run it

  1. Open Terminal (on Windows, Command Prompt), and go to the folder where you saved both, for example cd Downloads.
  2. Type this, with the archive's folder name and the code from the result record: 
    python3 recount.py pba-2026 --archive-sha256 <archive_sha256>
  3. Read the last line. Matches the published result. means every check passed and the count is the one that was published.

If you have the result record's transaction as a file, from any block explorer, give it instead of the code, and the tool checks the record's signature too: 

python3 recount.py pba-2026 --result-tx result.hex

From inside an unzipped archive, where the tool sits beside the files, name the folder as ., and add -I so Python loads nothing else from the folder: 

python3 -I recount.py . --archive-sha256 <archive_sha256>

That copy came with the archive, so compare it with the published recount.py, or read it, before you trust what it prints.

What it checks, in order

  1. Every file in the archive against MANIFEST.sha256, and the manifest itself against the result record's archive_sha256.
  2. The block headers: each one names the block before it, and carries the proof of work its own target asks for.
  3. Each transaction's bytes against its txid, and each merkle proof against the block header it claims.
  4. Every record, read again from the transaction bytes: the election, the voter roll and each ballot, with the signature over every field and the address that signed it.
  5. The counting rule, run again on what the transactions say.
  6. The tally and winners, against the archive's count.json and the result record.

What you see

Every ballot, in the order the chain holds them, marked counted with the candidates it names, or not counted with the rule it failed. Then the tally, the winners, and two block hashes you can look up anywhere.

A ballot can fail a rule and still be honest: a member may change their vote, and only their latest ballot counts (replaced). Others arrive too early or too late (before_open, after_close), come from a key not on the roll (not_on_roll), or carry no valid signature (no_signature).

If it doesn't match

The tool ends with Does not match. and lists each check that failed, naming the file or the transaction. It prints no tally, because a tally from a changed archive would mean nothing. Common reasons: a file changed or went missing in the download, or the archive_sha256 was copied wrong. Download the archive again, check the code, and run it once more. If it still fails, the archive isn't the one the result was published for, and that is worth telling the election's administrator and other members.

One check to make by hand

The tool proves the headers form a chain with real proof of work, but only you can tie that chain to the real one. At the end it prints the hash of the closing block and of the last block in the archive. Look up either height on any block explorer, or on your own node, and check the hash is the same.

What a recount can't tell you

  • Whether a ballot was left out of the archive. The archive holds every ballot Bitblocks found; anyone with their own copy of the chain can look for more.
  • Whether each address on the roll belongs to a real member. That is the roll's job, published by the organisation that ran the election.

For developers

recount.py is one file, Python's standard library only, with a small secp256k1 to check the signatures. python3 recount.py --self-test election_count_v0.json runs the counting rule's published test vectors and fails if any outcome differs. The format and the rule are in docs/ELECTION_DOGFOOD.md. Write your own recount against them; the vectors are there so yours and ours agree.
